# 飞书渠道交互升级方案

> 目标：把飞书从「纯文本进 → 展示卡片出」的单向管道，升级成**可交互**、
> **多模态**、且**由贾维斯自行决定表达形态**的双向渠道。
> 状态：核心已落地并通过单测（27 个测试文件全绿）；「官方 cardkit 流式」以
> 配置开关默认关闭、需真实飞书联调后再开。

---

## 一、升级前的接入模式（现状）

飞书桥 `lark_bridge.py` 走官方 `lark-oapi` 长连接（后台线程 + 独立事件循环），
能力面很窄：

- 只订阅 `im.message.receive_v1`，且**只处理 `message_type=="text"`**——图片 /
  文件 / 语音 / 富文本全被丢弃。
- 回复恒为一张展示型交互卡（JSON 1.0，`lark_md`），**没有任何按钮 / 输入 / 表单**。
- 需要用户「决策」时靠**打字**（如代码审查要打「激活 X」）——因为根本没接回调。
- 流式 = 每 0.8s 用 `PatchMessage` **整卡重刷**（有撞更新频率限制的风险）。

一句话：卡片本身不可交互，飞书只是个「只读大屏」。

## 二、飞书官方提供、本次接入的能力

| 能力 | 官方接口 | 本次是否接入 |
|---|---|---|
| 卡片回传交互（按钮/表单点击回调） | `card.action.trigger` | ✅ |
| 卡片 JSON 2.0（富文本/布局/流式） | `schema: "2.0"` | ✅ |
| 官方流式（卡片实体 + 增量推文本） | `cardkit-v1` | ✅（开关默认关，待联调） |
| 多模态消息接收（图片/文件/语音/富文本） | `im.v1.message_resource` | ✅ |
| 富交互组件（按钮/下拉/输入/表单） | 卡片 2.0 组件 | ✅ |

## 三、改造设计

### 核心接缝：按钮回调 = 合成一条「用户消息」

贾维斯控制器（`core/controller.py`）本就把工具产出的**带外动作**经
`drain_actions()` 交给各渠道自行渲染（文件下载、证件揭示、代码审查都走这条路）。
本次沿用同一接缝，**不给控制器加任何新分支**：

```
用户点按钮 / 提交表单
  → 飞书 card.action.trigger 回调（携带 value 与 form_value）
  → lark_bridge._on_card_action 把它翻译成一句「用户输入」
  → run_coroutine_threadsafe 喂回 _handle(open_id, intent)
  → 复用整条既有文本管线（含流式、历史、带外动作）
```

于是「点按钮」与「用户打了这句话」完全等价。每个按钮的 `value` 里塞一个
`__jarvis_intent__` 字段，其值就是点击后要重放的那句话——这句话由**模型**在
产出按钮时自己写（例如「激活 stock_quote」「确认发送」）。

### 让贾维斯自己决定「怎么发交互体验更好」

不硬编码「遇到 X 就发按钮」，而是把飞书的表达调色板告诉模型，再给它两把工具，
由它按内容自行挑选形态：

- **渠道画像**（`core/channels.py` 的 `lark` 档）改写为一份「什么内容用什么形态」
  的指引：普通回答走文字；要用户选择/确认→按钮；要收多个字段→表单；宽表→文件。
- **两把新工具**（`connectors/interactive_tools.py`，随 `discover_connectors` 自动注册）：
  - `send_choice_buttons(text, options)` —— 给用户一组可点按钮做选择/确认。
  - `send_input_form(text, fields, submit_intent)` —— 发一张表单一次收齐多个字段。

  两者都产出 **channel-agnostic** 的 `Action("interactive", …)`（`core/results.py` 的
  `present_options` / `present_form` 构造），各渠道各自渲染：飞书→2.0 回传卡，
  网页→可点卡片，后台→退化为文本。工具声明 `effect="write_local"`，不触发不可逆确认闸。

### 卡片构建：统一到 JSON 2.0

新增 `core/lark_cards.py`——**纯函数、零 SDK 依赖、可单测**的卡片构建层，是
1.0→2.0 迁移的唯一结构真源：

- `text_card` / `text_card_json`：标题 + markdown 正文（可选 `streaming=True` 打开
  2.0 流式模式、给正文组件稳定 `element_id`）。
- `interactive_card`：正文 + 一排回传按钮（`behaviors:[{type:callback,value:{__jarvis_intent__}}]`）。
- `form_card`：正文 + 表单容器（input / textarea / select_static）+ 提交按钮。
- `intent_from_callback(value, form_value)`：把回调翻译成用户意图的纯逻辑（含表单值拼接）。

`lark_bridge._card` 改为委托 `lark_cards.text_card_json`，发送 / 流式 patch 全部
复用，一处升级、全链路生效。

### 多模态接收

`_on_message` 不再只认 text。新增 `_message_to_text(msg)`：

- `text` → 原文；`post`（富文本）→ 抽取纯文本；
- `image` / `file` / `audio` / `media` → 经 `im.v1.message_resource` **下载到本机**
  `DATA_DIR/lark_inbox/`，返回一句带**本机路径**的转述，模型即可据此行动（识别证件、
  读入文档等）。真实资源只落本机、不外发。

### 官方流式（cardkit）——开关默认关、失败降级

`_handle` 的流式抽象成 `open → write → close` 三步，底下两种实现：

- **patch**（默认，proven）：占位卡 + 整卡 patch 刷新。
- **native**（`config.FEISHU_NATIVE_STREAMING=true` 时）：cardkit 建卡实体
  (`card.create`) → 发引用消息 → 增量推文本 (`card_element.content`)，飞书端原生
  打字机、免整卡重刷频率限制。**建卡/发送任一步失败即自动降级回 patch**，绝不影响
  回复落地。

> ⚠️ native 路径涉及 cardkit 多步握手，**无法在离线环境验证**，需在真实飞书环境
> 联调确认字段无误后再把开关打开；默认关闭时行为与迁移前一致（但卡片已是 2.0）。

## 五、飞书后台需要的配置

- 事件订阅：保持「长连接接收事件」。
- 事件权限：`im.message.receive_v1`（收消息）+ 机器人能力。
- **卡片回传交互回调**：确保应用已开启「消息卡片」的回调能力（长连接下由
  `register_p2_card_action_trigger` 接收）。
- 读取资源：给应用 `im:resource`（下载消息内图片/文件）相关权限。
- 若要开原生流式：应用需具备 cardkit 卡片实体相关权限，联调通过后设
  `.env` 里 `FEISHU_NATIVE_STREAMING=true`。

- `python3 tests/run_all.py` → 27 个测试文件全绿，无回归。
- 端到端（需真实飞书凭据，本地跑）：给贾维斯发消息看 2.0 卡；触发一次代码审查

## 七、回滚

改动以「加法 + 一处委托」为主。如需回退交互能力：删除 `connectors/interactive_tools.py`
即移除两把工具（画像里的引导语随之失效但无害）；`_card` 委托与 2.0 迁移可整体
还原为旧 1.0 模板。native 流式默认关，无需回滚。
