# 客户循环与 Breeze 设计方案

> 让贾维斯在 HubSpot 里替 Ned 打理「呆滞电子元件交易」的客户关系循环:夜里整理、白天你干活。
>
> 本文由一整轮讨论收敛而成(2026-07-25/26)。底层生意逻辑见 `工作流程与模式总结.md`;
> 贾维斯自身架构见 `进化路线图.md`。核心一句话:
> **确定性的活贾维斯直接驱动 HubSpot 界面,模糊/生成式的活交给 Breeze;账本在 HubSpot,情报在贾维斯。**

---

## 零、背景与硬约束

生意的本质是**关系资产的循环提取**——给过相关 excess list 的公司是资产,单次交易只是一次提取。
贾维斯要服务的就是这个循环的「感知—判断—记录—提醒」闭环,而不是买家侧或选品(本轮已排除,见第十二节)。

**四条硬约束,决定了所有形态:**

1. **没有 HubSpot 官方 API,也没有 Import-a-file / data-integration 权限。** 能用的只有:UI 里改属性(记录级编辑 + bulk-edit 弹窗,实测可用)、以及内置 AI「Breeze」。
2. **Breeze 只读、不写。** 它能批量写,但走它的「澄清→二次确认」链改数据既脆又让贾维斯确认一个自己没枚举的范围,不安全。写一律走 UI 驱动。
3. **账本 canonical 在 HubSpot,衍生情报 canonical 在贾维斯。** 账户/deal/contact 状态、Note、Task 存 HubSpot;轮数、诊断、回复提炼、唤醒理由、判断-结果对表存贾维斯自己的库。
4. **低调足迹(见第十一节)。** Ned 不向公司透露在用贾维斯;唯一硬规则是 CRM 里不留明文 AI 字样。夜间异步运行,错开白天。

### 贾维斯侧数据库(情报层,与 HubSpot 的配合)

**HubSpot 存「现在是什么状态」,贾维斯自己的库存「HubSpot 存不了或不该存的」——历史、推理、预测、以及贾维斯自己的操作日志。它是配合,不是竞争的第二个账本。** 至少要装:

- 每账户的 **sequence 轮次/发信历史**(冷启动重建、夜间更新)
- **回复分级历史**(Breeze 每次归类结果 + 日期)
- **轮数诊断结论**(留/换/弃 + 理由 + 联网发现)
- **唤醒理由**(HubSpot Task 只记「何时」,这里记「为什么」)
- **判断→结果对表**(每条预测带日期、事后填真实结果 → 回测燃料,见第十节)
- **jarvis-vs-Ned 写入日志**(哪条 Note/Task 是 jarvis 写的,CRM 外,见第十一节)
- **无主池开采状态**(抽样、命中率、批次,见第八节)
- 可选:**HubSpot 状态的带日期快照**(既做「昨天后谁动过」的变化检测,又当回测历史轨)

**防漂移铁律:每次读都以 HubSpot 为准,贾维斯库的缓存态绝不覆盖 HubSpot;它自己 canonical 的只有上面这些 HubSpot 不持有的东西(基本 append)。**

**复用优先(先查后建):** `core/entities.py`(kind=client 存每账户衍生事实)、`intel/signal_library.py`(带日期+衰减的记录,正是「判断→结果对表」的现成范式)、telemetry/artifacts(写入日志)大概率能承载大部分——先查够不够再考虑新表。

## 一、分工总原则

| 维度 | 走「贾维斯驱动界面」 | 走「Breeze」 |
|---|---|---|
| 性质 | 确定性:要精确、要全、要写数据 | 生成/判断:总结、分类、诊断 |
| 例子 | 读账户/deal 状态、改 priority、建 Note/Task、拉全量列表 | 总结邮件往来、给回信分级、数 sequence 轮数、判"该唤醒谁" |
| 为什么 | 代码点死元素,无 AI 变量,可复现 | 本就无唯一答案,正是 AI 该干的 |

一条铁律:**别让一个 AI 驱动另一个 AI 去做能直接做的事。** 哪怕同一操作,也把「读」(Breeze/驱动圈定)和「写」(贾维斯确定性落值)拆开。

## 二、Breeze 驱动(技术落点,已实测)

Breeze widget 跑在一个**同源 iframe**(chatspot-widget-ui)里。Playwright 用 frame_locator 进入——
**别用 iframe 序号定位,用「其 contentDocument 含 `rte-content`」找 frame。**

| 用途 | 选择器 |
|---|---|
| 输入框 | `div[contenteditable="true"][data-test-id="rte-content"]` |
| 发送 | `button[data-test-id="chat-send-button"]` |
| 答案容器 | `[data-test-id="assistant-message"]`(取最后一条) |
| 完成信号 | 最新那条答案内出现 `[data-test-id="assistant-message-actions"]`(赞/踩/复制) |
| 新对话 | `[data-test-id="new-thread-button"]`(aria: Start a new chat) |

**每次提问默认开新对话**(点 new-thread-button),避免夜间连问多账户时的长上下文污染;`ask(fresh=True)` 默认如此。

**完成判据用「事件锚点」,不是定时等待。** ⚠坑:`assistant-message` 计数含「Thinking/Counting」中间态占位(实测 4 条 msg 只 2 条终答),别用「actions 数 ≥ msg 数」;应判**最新一条 assistant-message 内部是否挂了 actions 排**,或发送键从 stop 态翻回 send 态。两段式:先等进入「生成中」确认真开跑,再等「完成 + actions 排」,避免误抓上一条旧答案。

**耗时**:计数类秒回;重查询(如"最久无活动 8 家")>45s。给 Breeze 查询留 **30–60s 超时,走后台 detach**。答案是自由文本,但能干净解析成结构化(实测 8 行 {name,date} 一次抽出);格式不定时丢给贾维斯 `structured.py` 按 schema 归一。

复用点:贾维斯 `prospecting/` 里的 `HubSpotBrowser`(hubspot_worker/hubspot_session/login_manager)已用 Playwright 驱动常驻登录 profile,处理了登录持久化/掉线检测/后台模式。驱动 Breeze 与写回都是在它之上增量加方法。**不需要 ego 等外部工具。**

## 三、账户分级模型:两轴六格

两个正交字段:

- **ACCOUNT TYPE = 关系耐久度**:Core(永不衰减的保险柜)/ Prospecting(带衰减时钟的试验台)。
- **PRIORITY = 当前热度**:hot / warm / cold。底层是**数值**(实测 5=Hot,需存映射)。

### Core 触发线 = 该账户有 ≥1 个 deal 记录(不论输赢)

资产是「给**相关** list 的供应商」,不是「给 list 的人」——Ned 遇到过给成品耳机/充电宝/电线 list 的无关账户。
「给过 list」太松;「成过单」太紧(这行没卖掉是随机常态,给了对口料没配到买家的好供应商不该被踢)。
而「是否为这批料建了 deal」正好是 Ned **亲手判过「相关」**的结构化代理。

> **承重工作纪律**:Ned 做一批料就建个 deal(哪怕最后没卖掉)。做了料却没建 deal,会导致好供应商被误判 Prospecting、甚至被衰减释放。相关性算一次可一鱼两吃:既定 Core、又喂「月度剔除不相关账户」工具。

### 六格筛选判据(已用 Advanced filters 核过可用字段)

| | Hot | Warm | Cold |
|---|---|---|---|
| **Core**(有 deal) | 有 open deal | 无 open deal 且 Last activity 在 N 天内 | 无 open deal 且 Last activity 超期/无(休眠仍留 Core) |
| **Prospecting**(无 deal) | Last Engagement 短窗内 | 中窗内有 engagement | 无 engagement / 休眠(衰减钟上) |

**可靠账户级字段**:`Number of Associated Deals`(有 deal)、`Number of open deals`(Hot 信号,免去"判断沟通是否 deal 相关"这个伪需求)、`Last activity date` / `Last Engagement Date`、`ACCOUNT RATING`、`Sequence Opt-Out`。
**搜不到的**:`reply`(账户级无「入站回信」字段)、`sequence` 只有 Opt-Out(无「进行中/第几步」,那是 contact 层)。

两个软点:①「近期/中窗」天数阈值是旋钮,交回测校;②Prospecting 热度是最糙的一块(账户层筛不出「对方到底回没回」),先用 Last Engagement 粗分、标「待回测校准」。deal 计数不分 owner,但账户已是 Ned 的、deal 几乎必是他的,当代理够用(可抽查)。

Core 三格特别干净(纯 deal 计数 + 活动日期);**priority 可由这套筛选算出→低风险、可放手自主写回**。
account type 的**升 Core 可自动**——它纯由「你建了 deal」机械触发,且 Core 永不衰减、无风险(一有 deal 就是 Core,不重叠);
只有**降级 / 释放回 Prospecting/无主池才留人工把手**(会武装「以你名义自动发衰减序列邮件」)。

## 四、回复路由器(回复路与每日清单的共同心脏)

**Breeze 读回信→归类,贾维斯按行执行。** 以工作流④光谱为骨架,补上 list 相关性、转介、客套:

| 回复类型 | Note | Task | 字段/其他 | 谁执行 |
|---|---|---|---|---|
| 发来**相关** list | 否(deal 即痕迹) | — | 你建 deal → 自动归 Core Hot | 你建 deal |
| 发来**不相关** list(成品料) | 短 Note | — | 标「相关性=否」喂剔除工具 | 自动 |
| 有兴趣·**暂无货**(带/不带时间) | ✓ | ✓ 唤醒(有时间设到点;无则默认 3 月) | priority→warm | 自动 |
| 有兴趣·**卡 NDA/流程** | ✓ | ✓ 超时提醒 | priority→warm | 自动;需你推进的进清单 |
| **已有渠道**(提到对手) | ✓ 记对手 | ✓ 长周期唤醒 | priority→cold | 自动 |
| **明确不做** | ✓ 记原因 | — | **Sequence Opt-Out** + priority→cold | Note/Opt-out 自动;释放进你清单 |
| **转介**("归 X 管") | ✓ 记转介 | — | 该公司下起新 contact 的 sequence | Note 自动;对外触达进你清单/草稿 |
| 纯客套 /"我看看" | 否 | 短周期跟进(用默认 3 月) | — | 自动 |

- **无回复不进这张表**——归第五节的轮数诊断轨。两条一个管「回了怎么办」、一个管「一直不回怎么办」。
- **哪种回复要 Note**:只在回复带「日后会改变你动作的信息」时写;纯客套不写。判据:**下次还想记得的,才写 Note。**
- **默认唤醒周期 = 3 个月**(暂无货又没给时间时;纯客套跟进同)。
- **Note = HubSpot 原生功能,英文书写**,格式:`YYYY.MM.DD + 来源人 + 内容`。例:`2026.07.22 Alice said they don't need to offload their excess.`
- **Task = HubSpot 原生功能**(不用贾维斯自己那套):挂在账户/contact 上、进 HubSpot 任务队列、不与贾维斯日历打架。贾维斯建 Task 时驱动 UI 建 HubSpot Task;每天用 `calendar.register_source("hubspot_wakeups")` 读「今天到期的 HubSpot Task」汇进简报。

## 五、三层架构

系统是三层,各按需触发,不互相顶替:

1. **批量 priority 分类器** —— 纯字段、粗热力图、全量、**自动**。跑第三节那套筛选给账户刷 hot/warm/cold。
2. **回复处理路(最重要)** —— 纯字段看不见「客户回了什么」,而「暂无货/以后有 list/已有渠道」是命脉(带时间的"以后有"最肥)。路径:夜间用 Last activity/Engagement 找「昨天后动过的一小撮」→ Breeze 读最新活动判是不是入站回信+说了啥+归④六格 → 贾维斯按第四节路由器执行(写 Note + 配 Task)。
3. **轮数诊断** —— Breeze 数已 log 的 sequence 轮数(它的甜区)→ N 轮无果时贾维斯介入:看 contact 是谁/人对不对、**联网搜这家值不值得继续** → 留/换人/弃。

后两层是 Breeze+贾维斯按需的小批量,不进全量夜扫——正好化解「信息量太大」的担心。

## 六、写回机制与自主边界

**三种改字段的方式,按量选:**

- **记录级编辑**(打开账户→属性栏按名字设值,一次一条)→ 稳态涓流。
- **bulk-edit 弹窗**(勾行→Edit→搜属性→填值→Update,一次 N 行)→ 冷启动/批量。步数多但每步都是死的表单控件,可自动。**选择器已实盘验证(2026-07-26)**:属性选 `bulk-edit-property-select`、值下拉 `property-input-*`(选项 role=option 文本 `5 (Hot)/3 (Warm)/1 (Cold)/0 (dead)`)、保存 `bulk-actions-edit-modal-save`。实现见 `prospecting/account_writer.py`(默认 dry-run=Cancel,apply=True 才 Update)。
- **不碰「点单元格」**(依赖横向滚动/列位置,最脆);Import 无权限,作废。

**priority 有第 4 档 `0 (dead)`**(实盘发现)——Ned 手动标"死账户"用。**分类器绝不产出 dead、也绝不自动覆盖现有 dead**(否则会复活判死账户);reconcile 里现有=dead → 桶 `skip_dead`、不写(dead 保护优先于一切)。

**自主 vs 审批边界(已定):**

| 动作 | 谁做 |
|---|---|
| priority 写回 | **贾维斯自动** |
| 写 Note、建 Task | **贾维斯自动** |
| 升 Core(有 deal 机械触发,永不衰减无风险) | **贾维斯自动** |
| 降级 / 释放回 Prospecting/无主池 | 给 Ned 清单,人工 |
| 任何对外(发触达/新 contact 触达) | 给 Ned 清单/草稿,人工 |
| 释放回无主池 | 给 Ned 清单,人工("我想不会太多,我自己来") |
| 从无主池认领 | 给 Ned 清单,人工(占产能) |

### 护栏合规(必须遵守贾维斯现有两道闸)

贾维斯已有两道运行时护栏,写回一律走它、不绕过:

- **effects 效应等级**:写 HubSpot = **`write_external`**(改外部系统)。⚠ 注册工具时**必须显式声明**——默认是 `write_local`,漏标会让写入偷偷跳过外部写与污染两道检查(这是最容易埋的雷)。降级+Sequence Opt-Out 标 **`irreversible`**(牵动"以你名义自动发信"),强制 ConfirmGate,且本就只进人工清单。
- **trust 污染闸**:同一回合读过外部不可信内容(尤其 Breeze 读客户邮件)后,禁止 `write_external`。

**据此的写入分两类:**

1. **分类器写入(priority/type 对账)——免确认自动写。** 它读的是结构化字段(deal 数/日期,非自由文本、无注入风险),读→出计划→写分阶段,夜间循环里直接落。
2. **回复派生写入(Note/Task)——走日报确认(方案 a)。** Breeze 读客户邮件是不可信内容,按污染闸不能同回合自动对外写。故回复处理路把「拟写的 Note/Task」放进**日报的「待确认」清单**(每条:客户/回了什么/拟写 Note 英文/建议唤醒日),Ned 一键或逐条批准 → 批准那一下=干净新回合 → 才写。既合规、又只需 Ned 点头。

## 七、夜间作业(= 一个夜间定时任务)

只碰「今晚有理由碰的」,绝不遍历。候选六条(待 Ned 最终勾选):

1. 有新回信的 contact → 回复路由器分类(第四节)
2. 有新活动的 ongoing deal → 更新往来总结
3. 今天到唤醒日的账户 → 进明天简报
4. 跨过「2 轮完成无回复」或衰减阈值的 Prospecting → 诊断(第五节)
5. 新转 closed-won 的 deal → 复购(问盘库、建唤醒 Task)
6. 今天有活动的账户 → 重算 priority

变化检测靠 `Last activity` / `Last modified` 找「昨天后动过的」。落在贾维斯现成的后台 detach + 交付(飞书)架构上。

### 简报(夜间作业的出口)

宗旨:**给 Ned 一份每日任务清单 + 近期简报**。所有夜间层跑完,把「要你动手的」汇成清单、「供你知悉的」汇成摘要。**按需装填——空的段落不出现,不拘顺序。**

- **今天该做的事(可执行清单)**:**待确认写入**(回复派生的 Note/Task,方案 a,一键/逐条批准)、该再 sequence 的、该换/找新 contact 的、到唤醒日该碰的、待你拍板的诊断结论、待你手动执行的释放/认领清单、需你回应的回复。
- **近期动态(摘要)**:最近成交(和谁做了 deal)、ongoing deal 状态变化、值得一提的回复。

每日 Task 到期就自动冒进这份清单(经 `calendar.register_source("hubspot_wakeups")` 读 HubSpot Task)。

### 轮数诊断阈值

Ned 节奏 = 3 封一轮、隔约 2 月再来。「一轮完成且无回复」= 3 封发完 + 2 月间隔已过 + 零入站(自动回复/离职通知不算,Breeze 判)。
**默认第 2 轮跑完触发诊断**(第 3 轮要花力气,先决定留不留再投);N=2 可回测调成 3。任一时点有回复 → 脱离此轨,转回复路由器。
诊断三桶 → 动作:人不对 → 换 contact 重开(对外,进清单);公司不行 → 释放(进清单);单纯没回 → 留、拉长唤醒。

## 八、无主池开采(独立周级批处理,不进夜扫)

约 5 万无主账户是**水库,不是工作量**。漏斗三步:

1. **P0 结构化筛**:无主(owner 空/非你)+ 有过互动(Last Engagement/曾被联系)+ 无 deal + 未 Opt-out → 把 5 万砍到小几千。
2. **排序**:按 Ned 验证过出货好的品类/区域。
3. **先舀 50–100 尽调、量命中率,再放量。** 速率 = min(Prospecting 550 剩余名额, 每周真能开发量),小批周更。

舀出来走第六节的认领清单——**给 Ned 清单,他点头再入池 + 起 sequence**。

## 九、冷启动 / 回填(全量、分批)

- **用 account 创建时间当固定游标**:它不可变,从旧到新一批批推,不会像滚动那样漏行/重复(解掉「抓不全」的老坑)。
- **每账户回填**:字段定级(priority/tier,走 bulk-edit)+ Breeze 数轮数重建进**贾维斯自己的库**。
- **不往 HubSpot 喷历史 Note**(效用低——信息本就在邮件时间线、Breeze 随时可读,补了还打乱时间线顺序;也顺带避免扎眼的批量倒填)。Note 只对往后新回复才开始流。
- 一次性、跨几天分批(Breeze 逐个较慢是唯一成本)。**重建出的历史顺带当第十节回测的离线数据集。**

### 首轮对账:现有分级 ≠ 新定义时怎么办

现有 type/priority 是混的(一部分是 Ned 真实人工判断、一部分是噪音,如 Breeze 测试把一批 Paragon 刷成 Hot),而 v1 分类器又偏粗——**两头都不能全信,故首轮出「对账差异表」让 Ned 过目,绝不盲目覆盖**。五桶(2026-07-26 首次真实数据跑通后细化,把 type 分歧按方向拆开):

| 桶 | 含义 | 处理 |
|---|---|---|
| `match` | 算出=现有 | 不动 |
| `fill_blank` | 现有 priority 空("--") | **自动填**(无值可毁) |
| `type_promote` | prospecting→core(有 deal 却没升 Core) | **自动升**(Core 永不衰减、安全),连 priority 一起写 |
| `priority_mismatch` | priority 分歧 | **自动纠正**(现有多为噪音,信任计算值;priority 可逆低风险) |
| `type_demote` | core→prospecting(标了 Core 却无 deal) | **人工**(降级会武装自动发信,高风险) |

**自动集 = fill_blank + type_promote + priority_mismatch;人工集 = type_demote。**(`account_grading.AUTO_BUCKETS`;`build_write_plan()` 拆成 auto / manual_demote 两清单)

**应用时机(Ned 2026-07-26 定):所有对账写入都不在搭建/测试期手动做,而是【第一次正式夜间循环】执行。** 搭建期只 dry-run 预览。

**现有值是噪音、不是判断(Ned 2026-07-26 确认)**:三个来源——① 继承过来的客户 ② 他以前自己手动操作的 ③ 全新导入被公司默认策略打标的。故不必把现有值当深思熟虑的判断来保护,**首轮可更信任计算值**;priority_mismatch 倾向直接按计算值覆盖(现有多为旧标),差异表留作 spot-check。

**type_demote 的重大修正(2026-07-26,实盘复核后)**:最初把「Core 但无 deal」一律当降级候选是**错的**——实盘发现里面混着大量合法 Core(Paragon Kunshan 本月新建、Triode 2021 老号但 2 月还有活动)。**核心原则:"Core=有 deal" 是给往后新账户配合纪律用的,不能追溯性地把你现有的真实 Core 关系降掉。** 现有 Core-marking 是你的真实判断,默认应保留。

故降级候选收紧成**真死号**:必须同时满足「建号 ≥90 天」且「最后活动 ≥180 天前(或从无活动)」且无 deal;任一不满足(新建 或 近期有活动)→ 归 `type_demote_recent` **暂放桶、不动**(`CORE_DEMOTE_MIN_AGE_DAYS=90`、`CORE_DEMOTE_MIN_INACTIVE_DAYS=180`,与文档「6 个月无活动才衰减」对齐)。

即便是收紧后的真死号清单,也**只是给 Ned 复核、绝不自动降**;真降时才配 Sequence Opt-Out(掐自动发信)。"6 个月自动序列"的风险只对真正 6 个月零活动的账户成立,别拿它吓唬活关系。

**这张差异表同时是分类器校准信号**:在 Ned 认为分对的账户上大量打架 → 先调旋钮再上线。

### 稳态防覆盖:尊重手动值,但「提出分歧、不当没看见」(协作原则)

每晚重算不能把 Ned 手动改的值冲掉。规则:贾维斯在自己库记下每次写入的值(`write_log.jsonl`);下次若现值 ≠ 它上次写的 → 判为人手动动过 → **退让不覆盖**(`customer_loop_store.should_auto_write`)。

**但"退让"≠"永远无视"(Ned 2026-07-26 校正的协作模式)。** 若只是静默跳过,那 Ned 一改某账户就永久脱离系统视野,这不是配合、是放弃。所以:**当算出的值 ≠ Ned 的手动值时,贾维斯把它收进「分歧提示」清单(账户 + 你设的 + 规则算的)进日报——它只提、不改,realign 与否 Ned 定。** 这条推广为通则:**贾维斯尊重人的手动决定、绝不擅改,但也不假装没看见分歧,而是摆出来供人裁决。**(实现:`nightly._incremental` 的 `分歧提示`。)

稳态只在需要时写(冷启动已把大多数刷成 match,每晚真正写的只是"昨天后热度变了的"少数)。

## 十、回测(整体视角)

打脸清单精神搬到这台关系引擎上。贾维斯做的「预测」= priority 分级、sequence 诊断、唤醒押注、释放决定。
**每个判断落成「带日期+证据的预测」,事后跟真实结果对表**:诊断"留着培育"下一轮真回了吗?唤醒"3 月后/盘库后"那天真要到 list 了吗?释放的后来重挖成了吗(漏杀)?P0 挖的多少真出回信(验证无主池论点)?→ 攒出每类判断命中率,回调阈值。

**北极星指标**(候选):季度拿到 excess list 数 + 休眠 Core 复活率。
**离线回测**:先拿冷启动重建的历史验诊断规则应验没,再上线,不拿真客户试错。

## 十一、低调足迹(硬约束)

威胁模型不严——公司不会盯每一条操作痕迹。**唯一硬规则:CRM 里不留明文 AI 操作字样。**

- **夜间异步 = 正式设计**:Ned 白天工作,贾维斯晚上整理、错开。夜间打标签/定级不会引起怀疑。
- Note/Task 的 author 走登录态 UI 本就**自动记为 Ned**;走 UI 而非 API/Import 天然像人手(无 API 权限在隐匿上是意外优势);Note 用 Ned 自定格式,与他自己写的一致、混得进。
- **jarvis-vs-Ned 的区分放在贾维斯自己 CRM 外的日志/artifact**(公司看不到,Ned 可回溯),不在 CRM 留标记。
- 诚实上限:能压很低,但有审计日志权限的管理员理论上仍可能察觉模式——别当绝对隐形。
