# 造工具能力诊断：oem_ems_screener 复盘

> 2026-07-18 · 起因：`skills/oem_ems_screener` 由贾维斯自建，通过了当时**全部三道验证门**，
> 真跑起来却是错的。本文记录根因分析与据此落地的框架改动。
>
> 结论先行：**现有护栏只验证「代码能不能跑」，不验证「跑得对不对」。**
> 前者是存在性问题（方法在不在、能不能 import），后者是语义正确性问题（用法对不对、
> 覆盖全不全）。造工具框架一~三期解决的全是前者，而这个案例里的缺陷全属于后者。

---

## 1. 案例：一个"全绿"却错的工具

原版 `oem_ems_screener` 的实际缺陷：

| # | 缺陷 | 后果 |
|---|------|------|
| 1 | 把 `column_index_map` 的值当成 `td` 位置下标（`cells.nth(idx)`） | 整列错位；退化时抓到 checkbox 列 → 全空 → 报"视图内未找到公司记录" |
| 2 | 用通用 `_extract_text` 取 name/owner，绕过 `_extract_name`/`_extract_owner` | owner 带邮箱后缀、name 可能串行 |
| 3 | 只读当前页，无翻页 | **静默数据截断**：`max_companies=0` 号称"全部"，实际只有第一页 |
| 4 | 调 `refresh_column_index_map()`，它硬性要求 domain 列存在 | 视图无 domain 列 → 必失败，且错误信息与 domain 无关 |
| 5 | `input()` 阻塞读 stdin + `print` 提示 | 服务进程无终端 → 卡死；用户在网页/飞书里看不到任何提示 |
| 6 | `resolve_paths(仓库根)`，与 app 的 profile 目录不同 | 另建一份 `chrome_profile`（仓库里 60MB 垃圾），**已登录仍要再登一次** |
| 7 | 判定不喂 domain，且"拿不准默认 false" | 同名公司误判；漏判静默混入 No，用户无从复核 |
| 8 | 模型取 `OPENROUTER_MODEL`（未导出）→ 恒回落 `gpt-4o` | 与 app 主模型不一致，成本与行为都不受控 |

## 2. 三道门为什么全绿

| 门 | 查什么 | 为什么没拦住 |
|---|---|---|
| `validate_tool_code` | 语法、import 黑白名单、SQL 注入、结构 | 上述缺陷没有一个是语法或危险 import |
| `check_building_block_usage` | 在 building block 上调用**不存在**的方法 | `_extract_text`、`rows`、`column_index_map` **全都真实存在**——它查的是"编没编"，不是"用没用对" |
| `smoke_import_skill` | 隔离子进程 import + 断言 TOOL_DEF | 刻意**不执行 handler**（避免真实副作用），而所有缺陷都只在执行时显形 |

三道门的共同盲区：**它们检查的是代码与代码库的一致性，而缺陷在于代码与「真实世界语义」的一致性。**

## 3. 四层根因

### 3.1 注入的 API 面 ≠ 真正要用的 API 面（最主要）

`building_blocks_api_text()` 原本只注入「公共签名」，即：

- `symbols` 只列了 `HubSpotBrowser` 一个类 → `resolve_paths`、`ensure_directories`、
  `SessionExpiredError`、`STEALTH_CHROMIUM_ARGS` **全都没注入**，但复用它们是必须的
  （原工具确实 import 了它们——靠猜，且猜中了，纯属侥幸）。
- 过滤掉所有 `_` 开头的方法 → 而**真正正确的提取逻辑全是私有的**
  （`_extract_name` / `_extract_owner` / `_column_idx`）。模型只看到 `rows()` 返回一个
  Locator，就只能自己造 `cells.nth()`。

**它不是不想用对，是根本没看见对的东西。**

### 3.2 只给签名，不给语义

即使签名给全，`column_index_map: Dict[str, str]` 也说不出「值是 HTML 的
`data-column-index` 属性值，不是位置下标」。这类**用错就出错、但签名表达不了**的约定，
必须显式写成自然语言注入。

同理：`refresh_column_index_map()` 的签名看不出它强制要求三列齐全；`rows()` 的签名
看不出它只返回当前页。

### 3.3 没有「运行环境契约」

模型不知道自己写的代码将跑在一个**没有终端、print 无人看、有头浏览器弹在服务器上**
的进程里。`input()` 在一个 CLI 脚本里完全合理——错的不是这行代码，是缺失的环境上下文。

### 3.4 没有「结果诚实性」要求

"只抓到第一页"本身不算 bug，**"只抓到第一页却宣称抓了全部"才是**。原提示词里没有
任何一条要求工具如实报告覆盖范围，于是模型默认按乐观路径写。这类缺陷最贵：
它不报错、不崩溃，只是让用户基于不完整数据做决策。

> 补充观察：该工具 meta 里 `last_change` 是 `manual update_tool_code`——最终版本是
> **原样写入**的，绕过了 `_author_verified_loop`。这个入口的存在是合理的（"我已写好代码
> 只想原样保存"），但它意味着最终产物可能从未经历完整验证循环。值得在 UI/返回文案上
> 明示这一点。

## 4. 已落地的改动

### 4.1 `core/skill_policy.py`（OPEN）

`BUILDING_BLOCKS` 每项新增四个可声明字段，`building_blocks_api_text()` 全部渲染：

| 字段 | 作用 |
|---|---|
| `constants` | 注入模块级常量的**真实取值**（选择器、列名），技能不必硬编码或猜 |
| `expose_private` | 显式声明「虽以 `_` 开头，但就是给技能复用的」方法，并在注入面标注 |
| `attrs` | 构造后可读写的实例属性 |
| `notes` | 语义约定：签名说不清、但用错就出错的部分 |
| `recipes` | 可直接抄的最小正确用法骨架 |

`hubspot_worker` 的 8 条 `notes` 逐条对应上表中的一个缺陷（列索引语义、取文本方式、
domain 硬依赖、登录方式、profile 目录、生命周期、sync API、分页诚实性）。

新增 `check_runtime_contract(code)`：把 `input` / `getpass` / `breakpoint` 列为**阻断级**。

注入面从约 700 字符增至约 4500 字符（≈1500 token）。这个代价买的是：模型不必靠猜。

### 4.2 `core/tool_builder.py`（🔒 PROTECTED —— 需人工审）

- `CODE_GEN_PROMPT` 新增两节：
  - **【运行环境契约】** —— 无终端、print 不可见、禁止无上限阻塞、有头浏览器在服务器端
  - **【结果诚实性】** —— 必须如实报告覆盖范围；判定类须有第三态；区分"确实为空"与"解析失败"
- `validate_tool_code` 新增第 6 步：调用 `check_runtime_contract`，阻断级。

> **动机**：提示词是软约束，模型可以忽略；`input()` 的后果（服务进程静默挂起、用户
> 零反馈）严重到值得一道机械门。**影响**：新增一个阻断条件，理论上可能误伤"确实想读
> stdin"的技能——但技能运行环境里 stdin 本就不可用，不存在合法用例。

### 4.3 `config.py`（🔒 PROTECTED —— 需人工审）

`_export_env_for_skills` 白名单增加 `JARVIS_DATA_DIR` / `JARVIS_DOWNLOAD_DIR`。

> **动机**：技能被禁止 import `config`，此前无从得知 app 的运行态目录，只能用
> `Path(__file__)/../../..` 猜出仓库根 → 另建 chrome_profile → 登录态不共用。
> **影响**：两项均为路径、非敏感；`MEMORY_ENCRYPTION_KEY` 等敏感项仍绝不导出。

### 4.4 `tests/test_skill_policy.py`（新增，46 项断言）

把上述护栏钉死：运行契约拦截有效且不误报、注入面必须包含私有复用方法/常量/语义/范例、
`BUILDING_BLOCKS` 声明的每个符号都要在源码里真实存在（防改名后静默漏注入）、
一致性检查仍能拦臆造方法且放行真实私有方法。

## 4.5 第二轮：业务背景注入（2026-07-18 晚）

重写工具的过程本身又暴露了一层更根本的缺口。**贾维斯缺的不是写代码的能力**——它写的
代码语法、import、结构都对，三道门全绿不是侥幸。缺的是**三条接触现实的通道**：

| 缺的通道 | 证据 |
|---|---|
| **看不到目标环境** | 它写 HubSpot 抓取工具却从没见过 HubSpot 页面，选择器全靠倒推。旁证：人类协作者猜的 5 个翻页选择器也只中 1 个——差别不在猜得准，在于**能不能去核对**。真实页面上正确写法是 `button[data-next-page='true']` |
| **看不到执行结果** | 冒烟只 import 不执行。旁证：刚写完「不要用第一个 td，那是 checkbox 列」的诊断，重写时仍在 `_page_signature` 里犯了同一个错，是离线验证台抓出来的，不是读代码读出来的 |
| **不会质疑需求** | 原始需求写着「max_companies 默认 0=全部」——**"全部"这个词本身就假设了不分页**，模型照做。重写过程中用户的 5 次纠正（视图 URL、owner 无关、fabless 归属、元器件原厂归属、总数实时变）**全部是需求层面的，没有一次是代码 bug** |

外加一条最容易补的：**有档案却没送到**。此前 `create_tool` 组装的提示词只有

```python
base = ref + f"工具名：{name}\n需求：{request}"
```

用户档案一个字都进不去。于是模型写「筛 OEM/EMS」的工具时，只能从需求字面出发问
「这家是不是真制造商」；而用户做 ESO 交易，真正该问的是「它在供应链的哪一端——
消耗元器件还是生产元器件」。后者**必须知道用户靠什么赚钱才问得出来**，档案里就写着。

**已落地**：`core/tool_builder.py` 新增 `_user_context_text()`，把 `profile.build_block()`
注入 `create_tool` / `edit_tool` 的生成提示词（约 190 token），并附三条用法说明：
按业务目的定判据而非字面直译、忽略无关个人条目、**做了需求里没明说的业务假设必须写进
工具 docstring** 让用户能一眼纠正。`JARVIS_TOOL_AUTHOR_PROFILE=0` 可关闭。
安全面无变化——档案本来每轮对话就注入 system prompt 发往同一个 OpenRouter。
测试见 `tests/test_skill_policy.py` 第 4 节。

**尚未做的三项**（按性价比排序，见第 5 节）：造工具前的需求澄清阶段、SELFTEST 钩子、
造工具时的环境探针。

## 5. 仍未解决

1. **"跑得对不对"仍没有机械验证。** 本轮把大量语义前移到了提示词与注入面——这仍是
   软约束。真正的解法是**带已知答案的小样本自检**：造完抓取类工具后，用一个固定输入
   跑一次，比对预期结果。设计成本不低，但这类工具若还会再造几个，值得做。
2. **子进程冒烟仍不执行 handler。** 这是刻意的（避免真实副作用），代价是执行期缺陷
   一律逃逸。可考虑给工具声明一个可选的 `SELFTEST` 钩子，冒烟时只跑它。
3. **`update_tool_code` 绕过验证循环**，最终产物可能未经完整验证——建议在返回文案里
   明确标注"本次为原样写入，未经生成-验证循环"。
4. **BUILDING_BLOCKS 的 notes 靠人工维护**，与源码之间没有强制同步。测试只校验符号
   存在性，校验不了语义描述是否过期。

## 6. 下一步的优先级

| 项 | 成本 | 收益 | 状态 |
|---|---|---|---|
| A. 业务背景注入 | 极低 | 高 | ✅ 已做（4.5 节） |
| B. 造工具前的需求澄清门 | 中 | **最高** | ✅ 已做（见下） |
| C. SELFTEST 钩子（冒烟时执行自检） | 中 | 中 | ✅ 已做（见下） |
| D. 造工具时的环境探针（写代码前看一眼目标页面） | 高 | 对抓取类工具决定性 | ✅ 已做（见下） |

### B 的实现（2026-07-18）

`_gather_clarifications()` —— 轻模型门控，在写代码【之前】判断有没有必须先问清楚的点。

**只问四类**，共同点是「猜错了不会报错，只会悄悄产出错的结果」：规模与分页、业务判据、
关键取舍、失败处理。每类都带一个真实事故做锚点（"全部"其实有 22 页；"筛制造商"
其实要的是供应链下游）。判断标准写死成一句话：*猜错了用户会拿到一份看起来正常、
实际是错的结果吗？*

**这个门最大的风险是变成盘问**，所以四条硬约束：

1. **只问一轮**：`create_tool` 新增 `clarifications` 参数，非空即跳过澄清门。
   结构上不可能来回拉锯。
2. **默认不问**：提示词里明确「多数工具不需要问任何问题，宁可不问也不要凑数」，
   并列出「绝对不要问」的黑名单（能用默认值决定的、纯技术细节、需求里已写的、客套话）。
3. **每个问题必须附带默认假设**，用户回「你看着办」也能立刻继续。
4. **失败即降级**：澄清调用出任何问题都返回空列表，绝不阻断造工具。

关掉：`JARVIS_TOOL_AUTHOR_CLARIFY=0`。测试见 `tests/test_skill_policy.py` 第 5 节
（11 项断言，重点钉住「只问一轮」和「默认不问」两条保证）。

> 遗留：`edit_tool` 暂未接澄清门。修改类需求通常更具体、且有现成代码做上下文，
> 盘问的负面效应大于收益；等 `create_tool` 上的实际表现有数据了再决定。

### C 的实现：SELFTEST 钩子（2026-07-18）

冒烟此前**只 import 不执行 handler**（为避免真实副作用），于是"能加载但结果是错的"
全部逃逸——列索引错位、静默只抓第一页都属此类。

现在工具可选声明模块级 `SELFTEST()`，它在隔离子进程里**真的被执行**（支持 async）。
约束写进了 `CODE_GEN_PROMPT`：只跑纯逻辑（不联网/不开浏览器/不读写文件），
用内置假数据，必须快且无副作用，重点测「猜错了不会报错、只会悄悄算错」的地方
（下标偏移、边界去重、单位换算、字段映射、分页终止条件）。

**防空测试**：`check_selftest_quality()` 静态检查——声明了 SELFTEST 却一个
`assert`/`raise` 都没有，直接判阻断级错误。理由写在错误信息里：*空测试比没有测试
更糟，它制造「已验证」的错觉*。这是 `self_iteration` 用「先红后绿」挡空测试的轻量版。

报错区分两类：`SELFTEST 未通过（工具能加载，但自检断言失败——逻辑是错的）` vs
`import/加载失败`——两者修法完全不同，混在一起报会把人带偏。

### D 的实现：环境探针 `core/env_probe.py`（2026-07-18，🔒 PROTECTED）

**这是把「人工用浏览器看一眼」固化成一次可复用的调用。**

门控设计（避免每次造工具都白开浏览器）：需求里**没有 http(s) URL 就直接跳过、零成本**，
绝大多数工具走这条；有 URL 才启动 headless 浏览器抽一份**结构摘要**注入提示词。

摘要抽什么（不是整页 HTML，那太费 token）：翻页/分页控件的真实属性、表头及其
`data-column-index` 之类的定位属性、一行的结构骨架（文本不带出）、页面自报总数、
主内容区的 `data-test-id` 清单。**顺序即优先级**——超出 `MAX_DIGEST_CHARS`(6000)
时从尾部截断，所以最有判别力的翻页控件排最前，价值最低的 id 清单排最后。
实测一张 HubSpot 列表页约 2200~3000 字符（≈1000 token）。

降噪很关键：原始输出一半是 `data-fdt-*`、`data-table-external-id`、每行都不同的实例
id、以及全局导航栏的 `data-test-id`，会挤掉真正有判别力的定位属性。现在有属性
denylist + 实例 id 泛化（`cell-0-2-name-6602561637` → `cell-0-2-name-*`）+ 只取主内容区。

**安全边界**：只导航 + 读 DOM，不点击/不填表/不提交/不下载；URL **只取自用户的需求
描述**，不接受从页面内容里发现的 URL（防注入）；只允许 http/https，拒绝带凭据的
URL；有超时；失败一律降级为空串。复用 app 的浏览器 profile 因而能看到已登录页面——
这也是它被划为 PROTECTED 的原因。关闭：`JARVIS_TOOL_ENV_PROBE=0`。

**效果验证**：拿真实的 HubSpot 视图跑了一遍，摘要里同时出现了
`data-next-page="true"`（那个谁都没猜到、而 5 个凭经验猜的候选只中 1 个的选择器）、
`pos=0` 的复选框列没有 `data-column-index`（列错位的根源）、
`532 records`（覆盖率自检的外部真值）。**本轮全部三个抓取类 bug，探针的输出里都直接可见。**

**补不了的**：业务判据本身（fabless 归哪边、分销商的制造部门算不算）无论多少工程
都要人拍板。所以设计原则不是「让它猜对」，而是**让它知道自己在猜，并把这个猜显式
摆到用户面前**——4.5 节要求「隐含业务假设必须写进 docstring」正是这个思路的最小实现。

## 7. 一句话总结

> 造工具框架一~三期让贾维斯**写得出能跑的代码**；
> 第四期补的是让它**写得出结果正确的代码**。
> 前者靠"存在性检查"，后者靠"把真实语义喂给它 + 要求它诚实报告自己的局限"。
>
> 而这一轮真正学到的是：**它写不好这个工具，主要不是因为不会写代码，
> 是因为它看不到目标环境、看不到执行结果、也不会追问需求。**
> 补前两条是工程问题；第三条是产品问题——得让它敢说"我不确定，你确认一下"。
