把"按文件分组"改为"按模型能识别的任务领域分组"，且组名互斥、无近似词。registry 的 group 是扁平字符串，所以下面全是扁平组（不引入层级，零代码改动即可）。

| `credentials` | list/reveal/update/delete_credential, ingest_credential_image | 不变 | 已经很干净 |
| `docvault` | list/ingest/update/delete_document | `documents`→`docvault` | 消除与 `document` 撞名；"文档保险箱" |

## 2. 描述改写规范（统一模板）

每条 description 按此结构写，缺项可省，但顺序固定：

```
<做什么(动词开头)>。<触发:用户说"…"时用>。<边界:不要用于…(指向兄弟工具)>。<关键参数提示>。<副作用/需确认>。
```

四条硬规则：
1. **每条都要有触发场景**（"用户说 X 时用"）——这是路由的主信号。
2. **有兄弟工具易混的，必须互相点名排除**（read vs ingest、list_credentials vs list_documents）。
3. **有副作用的（发消息/删除/开浏览器）描述里写明"执行前须确认"**——已有的保留，缺的补。
4. **参数语义在 description 里再点一次关键的**（如 alias 来源、cron 格式、fields 用法）。

> **已落地（2026-06-23）**：高价值的互斥/补边界改写完成——`list_credentials`↔`list_documents` 互相点名（消除"保险箱里有什么"撞词）、`read_document`↔`ingest_document_file` 读/存互斥、`send_file_to_chat` 强调"生成文件后必调"。delivery 5 工具在整合时已按规范重写。其余管理类工具（list/delete/pause_schedule 等）名义清晰，保持简洁。

## 3. 重点工具描述改写稿（仅列需改的）

**fileio — 读 vs 存必须互斥**

- `read_document`：
  > 读取本地文件并提取文字内容（PDF/Word/Excel/PPT/CSV/TXT/MD/图片）。用户说"读一下/看一下/总结/分析这个文件"时用。**只读取、不保存**；若用户是要把保单/合同存档，改用 ingest_document_file。path 必须是完整路径。
- `send_file_to_chat`：保持原意，补一句"凡是生成了文件（PDF/Excel/报告）后都要调用本工具把文件发到对话界面，不要只报路径"。

**docvault vs credentials — "保险箱里有什么"撞车**

- `list_documents`：
  > 列出**文档保险箱**（保单/合同/协议）的脱敏摘要。用户问"我有哪些保单/合同""XX 保单何时到期"时用。查证件/银行卡请用 list_credentials。
- `list_credentials`：
  > 列出**证件保险箱**（证件/银行卡/身份证/护照）的脱敏摘要。用户问"我有哪些证件/卡""XX 证件何时到期"时用。查保单/合同请用 list_documents。
- `ingest_document_file`：补一句"**保存归档用，不用于临时阅读**；只想看内容用 read_document"。

**intel — 几条过于简略**

- `signal_report`：
  > 取最近 N 天市场信号并按类型分组，**供生成电子元件市场情报日报**。用户/定时任务要日报数据时用。days 默认 14。
- `signal_hot_sectors`：
  > 列出余料信号聚集、值得提前跟进的赛道（机会轨行业级触发）。用户问"哪些赛道最近余料多/值得关注"时用。threshold 默认 6.0。

**delivery + availability —— 已于 2026-06-23 整合（8→5）**

两者本质是一个子系统（同一 `delivery_state.json`），已合并为 5 个 `delivery_*` 工具，`connectors/availability.py` 已删（`core/availability.py` 库层保留，仍被 web/intel 看板等复用）：

- `delivery_status`（增强：状态 + 休假区间 + 默认策略 + 临近待确认 id，吸收原 `availability_pending`）
- `delivery_pause` / `delivery_resume`（保留清晰动词）
- `delivery_rest(action=add/clear/confirm)`（合并 `delivery_set_rest` + `delivery_clear_rest` + `availability_confirm`）
- `delivery_vacation_default`（原 `availability_set_default` 改名）

双重休假机制的路由混淆已消除：所有休假区间操作都归 `delivery_rest`，默认策略归 `delivery_vacation_default`。

其余工具（credentials 组、profile、reports、workflows、authoring、scheduling）现有描述已达标，按 §2 模板抽查补齐即可，不逐条重写。
