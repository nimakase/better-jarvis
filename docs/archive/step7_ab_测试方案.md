# step7 工具渐进披露 —— A/B 测试方案

## 1. 假设与待决策

**假设**：当工具数量较多时，每轮只暴露「核心工具 + `load_tools`」能让 deepseek-v4-flash
路由更准（少被无关工具干扰），代价是偶尔多一轮 `load_tools` 和「该加载却没加载」的漏召。

**要回答的问题**：开启 `JARVIS_PROGRESSIVE_TOOLS` 后

1. 路由准确率是否提升 / 是否非劣？
2. 代价（额外轮次、漏召、误把闲聊也去 `load_tools`）是否可接受？
3. 收益是否依赖把 `general` 拆成更细的组？

**决策**：只有 B 在主指标上 **≥ A − ε（非劣）且无关键类回归**，才考虑默认开。

## 2. 两个臂（唯一变量＝开关）

| 臂 | 配置 | 说明 |
|----|------|------|
| A（基线）| `JARVIS_PROGRESSIVE_TOOLS` 未设 | 每轮全量工具，现状 |
| B（处理）| `JARVIS_PROGRESSIVE_TOOLS=1` | 核心 + `load_tools`，按需加载 |

模型、temperature、system prompt 注入、记忆、历史压缩都保持与生产一致。B 多出的
`load_tools` 提示段属于处理的一部分，不另作控制。

可选次要轴 **C**：B + 把 `general` 拆成 `feishu/document/credentials` 子组（只改连接器
`group=` 元数据），用来判断「收益是否需要更细分组」。

## 3. 评测集设计

按场景分桶，每桶 5–8 条、覆盖各 `registry` 分组；每条标注 **期望工具集**（正确答案）。
关键是把能区分两臂的情形放进去：

- **多干扰单目标**：存在大量工具、正确工具属某个小众组（B 应受益）。
- **隐藏工具诱惑**：用户要的功能其工具在未加载组——看 B 是否会 `load_tools` 发现，
  还是臆造工具名 / 放弃（B 的主要风险）。
- **非核心组目标**：正确工具在某领域组——量化 B 多花的 `load_tools` 轮次。
- **跨域单轮**：一条消息要用两个组的工具（B 可能需两次 `load_tools`）。
- **核心即可**：只用 `query_memory/write_memory/send_file_to_chat`——两臂应几乎一致（健全性校验）。
- **无需工具（闲聊/常识）**：检验 B 是否会**误**调 `load_tools` 或工具（误召）。

建议规模：**25–40 条 × 每条重复 10–15 次 × 2（或 3）臂**。模型有随机性，必须多次重复看「率」而非单跑。

## 4. 指标

主指标
- **任务级正确工具率**：在 ≤MAX_TOOL_ROUNDS 内最终调用了期望工具（且没调错关键工具）。

次指标（路由质量）
- **首工具命中率**：第一个非 `load_tools` 调用就是期望工具。
- **错召率 / 臆造工具名率 / 漏召率（该调没调）**。
- **无需工具类的误召率**（B 专看是否乱 `load_tools`）。

代价指标
- **平均工具轮次**（B 含 `load_tools` 轮）、**到首个有效工具的轮数**。
- **每轮工具负载 token**（≈ tools JSON 字符数/2）—— B 应显著更低。
- **每条总 token / 总轮次**（成本+延迟代理）。

B 专属
- `load_tools` **加载了正确组**的比例；平均多出的轮次。

## 5. 跑法（离线 harness，不产生真实副作用）

用脚本驱动 `JarvisController`，每条用例开一个全新会话，跑两（三）臂、各 N 次：

1. **隔离副作用**：monkeypatch `core.controller._execute_tool`，记录被调工具名+参数，
   返回一段**预置的合成结果**（按期望工具给个可信文本，否则通用 "OK"），让多轮/`load_tools`
   流程照常推进，但绝不真打飞书 / 写记忆 / 发文件。`load_tools` 在执行步之前就被拦截、
   只改 `active_groups`，本身安全。
2. **采集**：每次跑记录 调用序列、是否命中期望、轮次、tools 负载大小、token 估计、最终文本。
3. **切臂**：进程级设 `JARVIS_PROGRESSIVE_TOOLS`（B 前 `importlib.reload(config)`），或参数化跑两遍。
4. 结果落 CSV/JSON，便于复算与留档。

> 注意：harness 在 `/tmp` 或 outputs 里写+跑（本仓库挂载盘对 bash 读写不稳，见架构文档第 9 节同款问题）。

## 6. 统计与判定

- 同一批用例配对比较（paired）：对每条用例算两臂的成功率，再聚合。
- 报**差值的置信区间**（bootstrap 或比例检验），不要只看点估计；关注方差。
- **预注册判定门槛**（先定后看）：
  - 默认开 ⇐ B 任务级正确工具率 ≥ A − 2pp（非劣），**且** 每轮工具 token 明显下降，
    **且** 隐藏工具发现率、无需工具误召率均无超阈回归。
  - 若 B 准确率明显更高、CI 不含 0 → 强证据，默认开。
  - 若仅在轴 C（拆分 `general`）下才达标 → 先做分组拆分，再开。
  - 否则保持默认关。

## 7. 已知混淆与陷阱

- 多数工具仍 `group="general"`，B 的精简幅度有限；务必跑轴 C 判断收益是否依赖拆组。
- `load_tools` 菜单 token 也占成本，统计 token 时要算进 B。
- 模型随机性大 → 重复次数不足会得出噪声结论。
- 合成工具结果若与真实差异过大，可能影响模型后续决策；对关键用例用更贴近真实的预置结果。
- 评测集要包含「正确答案就是不调工具」的样本，否则会奖励过度调用。

## 8. 产出

一张对比表（A vs B[, vs C]：各指标点估计 + 差值 CI）+ 若干失败 transcript 摘录 +
一句按第 6 节门槛得出的「开 / 不开 / 先拆组再开」结论。
