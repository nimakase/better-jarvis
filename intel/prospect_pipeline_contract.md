# 潜客流水线 · 最终名单契约（Prospect Pipeline Contract）

> 定义「潜客生成 → HubSpot 富化 → 排序 → 交付」整条链流动的**富记录**结构与排序规则。
> matcher、潜客生成、情报台三处都照此契约对接。
> 版本 **v0.5**（瘦身：删历史库/assemble/track 列；降级路径改为存盘-通知-续跑，见 §11）。

---

## 1. 核心原则：matcher 退为「富化步骤」，不再是最终格式

老 matcher 把一切压成 6 列（company/domain/status/owner/计数），丢掉了生成层辛苦查来的一切（判定类别、把握、依据、排名）。新设计反过来：

```
潜客生成（公司 + category/confidence/evidence）
        ↓
候选落盘（checkpoint：下游任何失败都不浪费这次生成，重跑直接续）
        ↓
HubSpot 富化（matcher：只往每条记录贴 HubSpot 状态，不新建表）
        ↓
多级排序（CRM 状态 > confidence）
        ↓
名单交付（xlsx + 情报台「今日名单」）
```

matcher 的爬虫内核 `HubSpotBrowser.search` 原样复用；只改输入输出——**输入富记录、输出并回富记录**。

---

## 2. 富记录 schema（最终每行带的字段）

| 字段 | 来源 | 说明 |
|---|---|---|
| `rank` | 综合计算 | 最终排序位次（多级排序，见 §4；v0.4 起不再有合成的 `weight` 列） |
| `hubspot_status` | matcher | `matched` / `no_match` / `multiple_exact_matches` / `matched_owner_empty` |
| `hubspot_owner` | matcher | 认领的销售（如有） |
| `crm_state` | matcher 派生 | `new` 新客 / `unowned` 在库未认领 / `owned` 已认领 / `review` 多重待核 |
| `company_name` `website` `country` | 生成 | 基础信息（website→matcher 的 domain） |
| `category` | 生成 | `oem` / `ems` / `module`——与 `oem_ems_screener` 技能**同一套词表**（同一业务不能有两套客户定义） |
| `confidence` | 生成 | 0–100，生成层对"这家确实符合画像"的把握。查不到信息时降 confidence，**不是丢弃**（absence of evidence ≠ evidence of absence） |
| `evidence` | 生成 | 实际查到了什么、在哪查到的。没有它名单无法核实，只能全信或全不信 |
| `contact_rationale` | 生成 | 这家造什么产品、板级用到哪些元件、用量级别（**可核实的事实**）。v0.3 起**不再**写"为什么现在可能有余料"——那是信号库用真实证据判断的事，模型猜的没有价值 |
| `components` | 生成 | 元件大类 |

> **v0.5 删掉的两列**：`track`（恒为 coverage，全仓库无读取方）与 `seen_before`
> （历史库整条移除——跨批重复率低，不值一个存储层 + 两个工作流步骤；
> 偶发撞车由人在表里自行判断）。

---

## 3. CRM 状态映射（matcher 结果 → crm_state）

| matcher 返回 | crm_state | 含义 |
|---|---|---|
| `no_match` | `new` | HubSpot 里没有 → 全新潜客 |
| `matched` + owner 空 | `unowned` | 在 CRM 但没人认领 |
| `matched` + 有 owner | `owned` | 已被销售认领 |
| `multiple_exact_matches` | `review` | 多重命中，待人工核 |

---

## 4. 排序：多级显式排序（v0.4，v0.5 减为两级）

```
CRM 状态  >  confidence
```

| 级 | 依据 | 顺序 |
|---|---|---|
| 1 | `crm_state` | `new` → `unowned` → `review` → `unknown` → **`owned`（压底）** |
| 2 | `confidence` | 降序，把握大的先打 |

> **已认领公司不删除**：留在名单里、排到最底部、打 `crm_state=owned` 标记，你自己判断要不要再碰。
> 于是「HubSpot 里还没人碰 + 把握大 + 没出现过」的公司自动排最前——那是最该打的。

**为什么不再有合成的 `weight`**：v0.1–v0.3 是 `weight = intent_score × crm_multiplier`。
那时 `intent_score` 是信号驱动的真实强度，两个量相乘有意义。v0.4 把信号解耦掉之后，
若改成拿 `confidence` 去乘 CRM 系数凑一个小数，那是**假精度**——两个不同性质的量相乘，
小数点后三位不代表任何东西，还会让人误以为它精确。多级排序把每一级摊开，
谁排前面、凭什么排前面，一眼能看明白，你也能在表里按任一列自己重排。

**没有降级排序了（v0.5）**：HubSpot 未登录时**不出名单**——候选存盘、通知去登录，
登录后重跑直接续跑匹配（见 §11）。于是 `crm_state=pending` 这个半成品状态不复存在，
到得了表上的名单一定是匹配过的。

## 5. 名单只有一条轨（v0.2 起：机会轨已迁出）

- **覆盖轨**（coverage）：当天潜客树节点生成的 ~100 家，富化 + 排序后**就是名单全部**。

> **v0.1 → v0.2 的有意变更**：原设计让「信号点名的具体公司」以 `track=opportunity`
> 混进同一份名单。实践中这条路是错的，已迁往**市场情报日报**的「点名公司（金线索）」
> 板块（`intel/report.py`），潜客名单不再含机会轨记录。

三条理由：

1. **打分尺度不可比**。覆盖轨 `intent_score` 是命中信号强度求和（无上限）；机会轨是
   `severity × 2`（封顶 10）。两者放进同一列排序，等于拿不同量纲的数字比大小——
   排出来的名次没有意义。
2. **资格口径不一致**。覆盖轨的公司过了客户画像判定（消耗板级元件做制造的
   `oem`/`ems`/`module`，见 §9）并带 `confidence`/`evidence`；机会轨直接来自信号，
   **一道筛都没过**，可能是分销商、也可能是元件原厂。把「已核实合格」和
   「信号提到过」混在一张表里，会让整张表的可信度降到后者的水平。
3. **队列 vs 快照**。名单是**队列**——照着它打电话，做完了明天该换新的，同一家天天
   重出就是缺陷。日报是**快照**——回答「最近行业发生了什么」，三天前的关厂消息今天
   仍然该在。原实现每天把库里所有点名公司重新捞一遍塞进名单（`company_pointed_signals`
   是全库唯一没有强度衰减、也没有窗口的查询），正是把快照当队列用：跑两个月后每份
   名单都拖着累积的全部点名公司。挪进日报后它继承日报的 `days` 窗口，
   重复不再是缺陷而是正确行为。

**已知代价（有意接受）**：点名公司不再过 HubSpot 匹配——日报是纯渲染、不跑浏览器，
所以它告诉你「Doomed Robotics 关厂了」，但不告诉你这家是否已被销售认领。要跟进就
走潜客那条链单独查。

已认领压底逻辑仍照 §4，只是现在只作用于覆盖轨这一条轨。

---

## 6. 交付形态

1. **xlsx**：列即 §2 字段，按 rank 排好；已认领段落置底、浅灰底。
2. **情报台「今日名单」**：同一份数据在前端表格化，徽标显示 `crm_state`、附 `confidence`，一键下载 xlsx。
3. **早报推送**：取名单 top N 作为「今日要点」的线索部分。

---

## 7. 现有 matcher 要改什么（worker.py / service.py）

- **保留**：`HubSpotBrowser`（爬虫内核）、`exact_match` / `process_one`（匹配算法）不动。
- **改 `process_file` 的 I/O**：
  - 输入从「读 Excel(company,domain)」改为「接收富记录列表」。
  - 每条调用 `process_one` 得到 status/owner 后，**派生 crm_state 并回原记录**（不丢字段）。
  - 输出从「写 6 列 Excel」改为「写 xlsx + 返回记录列表」，按 §4 多级排序、已认领置底。
- **去掉**：Web 任务表/队列那套（service.py 的 TaskManager）——集成进 jarvis 后用 jarvis 的调度，不需要。

## 9. 客户画像口径（v0.3 校正）

**入选条件只有一条：这家公司采购并消耗板级电子元器件来制造产品。**

v0.1–v0.2 的生成提示词要求模型去找「手上可能积压、或经营困难/可能被收购」的公司。这是错的，两个原因：

1. **任何正常经营的制造企业都常年产生 excess**——产品改版、超订、EOL 最后一次采购、工程试产尾料、客户砍单，都是日常。能不能收到货取决于关系和时机，不取决于这家是否出事。按「出事」筛，会把名单缩窄到只剩困境企业，漏掉绝大多数正常客户。
2. **「现在哪里在冒余料」本来就有更可靠的判断者**——信号库用真实新闻证据算，模型猜的既无法核实也没有增量。让模型猜等于用低质来源覆盖高质来源。

于是分工收敛为：**模型判断「是不是用电子元件造东西」（可核实的事实），信号库判断「现在哪里有余料」（证据驱动），代码合成打分。**

### 判定词表与 `oem_ems_screener` 统一

同一个业务不能有两套客户定义。生成提示词与该技能共用：

- **合格**：`oem`（自有品牌造电子设备）、`ems`（EMS/ODM/PCBA 代工/box-build）、`module`（买元件做模组组件）
- **不合格**：`component_maker`（半导体/被动件/连接器/裸板等**上游**）、`distributor`、`design_house`、`service`、`other`

> ⚠ v0.2 之前写的是「用板级电子元件造整机/系统的 **OEM**」——这个措辞把 **`ems` 与 `module` 挡在门外**了。而代工厂常年接不同客户的单、频繁换线、持有寄售与缓冲库存，恰恰是最容易积累呆滞料的一类客户。这是个实打实的误伤。

### 规模：从「卡人数」改为「分档判断」

原先是硬门槛 200–2000 人。这是错的：人数只是**代理指标**，真正要判断的是「有独立采购决策权、有真实用量、够得着」三件事；而且欧洲大量私营企业不公开人数，硬筛的实际效果是逼模型去猜，猜出来的数字又和查证过的长得一模一样。

现在改为五档 `size_tier`，**重点看采购结构与产线而非人头数**：

| tier | 特征 | |
|---|---|---|
| `startup` | 单一产品线、无自有产线 | 排除——用量太小 |
| `small` | 单厂、有自己下单的采购 | 可要，优先级低 |
| `mid` | 自有产线 + 独立采购团队、多产品线 | **理想** |
| `large` | 多厂区，但厂级/事业部仍有采购决策权 | **理想** |
| `giant` | 采购集中总部、走全球框架协议 | 排除——够不着 |

关键在于**写明排除的理由而不是规模数字**，模型判断边界情况才有依据：一家 3000 人但采购分散在各事业部的公司算 `large`（老门槛会误杀它）；一家 800 人但完全是跨国集团生产基地、采购由总部统一走框架的，实质是 `giant` 的一部分（老门槛会放它进来）。

> `size_tier` / `size_basis` **不进 xlsx、不参与排序**。它们是给**模型**的筛选口径，不是给人看的数据——公司既然已经进了名单，知道它是 mid 还是 large 并不改变你要做什么。保留输出仅为**审计筛选是否生效**（整列 mid/large 说明正常，冒出 giant 说明漏了）。

### 不确定性靠 confidence 表达，不靠丢弃

`confidence` 0–100 诚实校准（90+ 官方来源明确、70–89 强间接证据、50–69 仅从名称/行业推断、<50 基本靠猜）。**绝不能因为查不到信息就判定一家公司不合格**——那是 confidence 低，不是排除。配套要求 `evidence` 写明实际查到了什么，否则名单只能全信或全不信。

## 10. 与信号库彻底解耦（v0.4）

**潜客名单不再读信号库。** `prospecting` 包不 import `intel.*`（由 `tests/test_prospecting.py` 用 AST 钉死）。

### 为什么

两条线服务的是**不同的业务动作，节奏和粒度都不匹配**：

| | 潜客名单 | 信号 |
|---|---|---|
| 服务什么 | **0→1 大范围开发**：每天一批新公司，去建立关系 | **存量决策**：手里的货要不要压、回头找买过某元件的老客户 |
| 周期 | 以**月**计（从第一通电话到成交） | 时效以**周**计 |
| 粒度 | 公司级 | 赛道级 / 元件级 |

「这周工业自动化在冒余料」并不改变你要不要给 Alpha Robotics 打第一通电话。而且信号是赛道级的——**一整个赛道的候选公司拿到同一个意向分，在一批名单内部几乎没有区分度**，只是让不同日子的名单互相不可比而已。

> 任何正常经营的制造企业都常年产生 excess（改版、超订、EOL 最后一次采购、试产尾料、客户砍单）。能不能收到货取决于关系和时机，不取决于这家公司此刻是否出现在某条新闻里。

### 移除了什么

- `generation.attach_intent()` 与 `TYPE_LABEL`（信号标签表）
- 工作流的 `signal_check` 步与「信号已 N 天未更新」横幅
- 记录字段 / xlsx 列：`intent_score`、`intent_tier`、`weight`、`surplus_signals`、`sources`
- `select_node()` 返回的 `node_sectors`
- 潜客树的 `signal_sectors` 字段与 `signal_vocab`（树 v3.0）
- `login_manager` / `make_hubspot_runtime` 借道 `signal_library._DATA_DIR` 拿 profile 路径的写法——改为直接读 `config.DATA_DIR`。借一个情报侧模块拿路径会让「已解耦」变成假象：import 还在，只是没用它的数据。

### 信号那边完全不受影响

采集、市场情报日报（价格供需动态 / 行业事件 / 热点赛道 / **点名公司金线索**）、`expire_stale` 全部照旧。信号仍然是有价值的资产，只是它的消费者是**情报台和日报**，不是潜客名单。

## 11. 降级路径：存盘-通知-续跑（v0.5）

**旧路径（已废除）**：HubSpot 未登录 → 全批标 `crm_state=pending` 照样出表，表头挂
"恢复后可一键补匹配"。两个实质问题：① "补匹配"功能从来不存在；② 降级批照样
`mark_done`，这个 (类目,区域) 被标成已完成，重跑会选到下一个节点——**降级批永远
不会被补上匹配**，LLM 生成的候选等于半废。

**新路径**：

```
generate 成功 → checkpoint（候选落盘 pending_batch.json）
     ↓
preflight 失败（未登录）→ 通知你去「本地调试」登录 → StopWorkflow 干净收尾
                          （不出表、不 mark_done、不清存盘批）
     ↓
登录后重跑 prospect_daily → select 发现存盘批 → 跳过生成直接 enrich
     ↓
出表 → mark_done → 清掉存盘批
```

要点：

- **checkpoint 在 preflight 之前**：不只未登录，enrich 中途崩、断电，重跑都从存盘批续，生成的钱只花一次。
- **不出半成品名单**：没匹配 CRM 状态的名单会让销售打给同事已认领的客户，宁可晚一天。
- **树全部跑完**同样走 StopWorkflow 干净收尾（提示可 `python -m prospecting.reset` 复位重扫），不再抛 RuntimeError 装故障。
